## 1. Executive Summary

**핵심 업무의 트랜잭션 경계와 DB 제약은 대체로 견고하다.**
- 요청 하나 = 트랜잭션 하나이며, 업무 변경과 감사 기록은 같은 commit으로 저장된다.
- 출결·성적·수업·평가·메시지는 행 잠금과 DB 트리거 버전으로 Lost Update를 막는다.
- 중복 생성은 UNIQUE·부분 UNIQUE·EXCLUDE 제약이 최종 방어한다.
- 메시지 발송은 메시지 행 잠금 + 성공 1회 부분 UNIQUE + 멱등 키 UNIQUE로 중복 발송을 막는다.
- 기존 동시성 테스트(동시 출결·성적, 동시 확정, 동시 발송·키 재사용, 재시도 직렬화, 동시 등록, 동시 배정)는 오늘 전체 실행에서 모두 통과했다.

**발견한 문제는 4건이다.** Critical·High는 없다.

| ID | 심각도 | 요약 | 재현 |
|---|---|---|---|
| INT-01 | **Medium** | 메시지 발송의 원본 검사 TOCTOU: 검사 후 commit 전에 출결·성적·연락처 변경이 끼어들면, 바뀌기 전 내용으로 발송 처리된다. 실제 창은 발송 1건당 **15~29ms** | **재현함** |
| INT-03 | Low | 평가 생성이 연결할 수업을 잠그지 않아, 동시에 취소된 수업에 평가가 연결된다 | **재현함** |
| INT-04 | Low | 같은 업로드 확정을 동시에 두 번 보내면 데이터는 정상이지만, 늦은 요청이 엉뚱한 409("같은 이름 학생")를 받는다 | **재현함** |
| INT-02 | Low(잠재) | 일괄 발송에서 원본 재검사가 SQLAlchemy 객체 수명에 의존한다(현재는 정상) | 현재 코드 **미재현**, 조건 변경 시 재현 |

그 밖에 Informational 6건이 있다(8절). 특히 **실제 문자 발송을 도입하기 전**에는 발송 I/O를 트랜잭션 밖으로 빼는 설계(아웃박스)가 필요하다.

**최종 판정: CONDITIONAL PASS.** 데이터 유실·중복은 발견되지 않았다. INT-01·03은 작은 수정으로 닫을 수 있다(9절).

## 3. 트랜잭션 구조·잠금·격리 수준 (Stage 1)

**세션**: `get_db()`가 요청마다 세션을 만들고 예외 시 rollback, 끝에서 close한다. `autoflush=False`, `expire_on_commit=False`. 서비스가 commit을 책임지고, Repository는 조회만 한다. 오류 경로는 `_abort()`가 rollback으로 잠금을 먼저 풀고 응답한다.

**잠금·버전 사용 현황**

| 쓰기 경로 | 잠금 | 동시 수정 감지 |
|---|---|---|
| 출결 저장 | 수업 `FOR SHARE` → 출결 행 `FOR UPDATE` | 항목별 `version`(DB 트리거가 UPDATE마다 +1) |
| 성적 저장 | 평가 `FOR SHARE` → 결과 행 `FOR UPDATE` | 항목별 `version` |
| 학생 한 명 기록 수정 | 수업 `FOR SHARE` → 출결·평가(`SHARE`)·결과 `FOR UPDATE` | `result_version`, 점수별 `version` |
| 수업 수정·취소 | 수업 `FOR UPDATE` | `version` + 기록이 있으면 취소·날짜 변경 거부 |
| 평가 수정 | 평가 `FOR UPDATE` | `version` + 만점 < 최고 점수면 거부 + DB CHECK·FK `ON UPDATE CASCADE` |
| 평가 생성 | **수업을 잠그지 않음**(INT-03) | — |
| 휴원·복귀 | 수강 `FOR UPDATE` | EXCLUDE 제약(기간 중복), 상태 동기화 트리거 |
| 연락처 수정 | 학생 `FOR UPDATE` | 버전 없음(마지막 저장 우선, INT-I3) |
| 메시지 편집·검토·확정·취소 | 메시지 `FOR UPDATE` | `version` |
| 모의 발송·재시도 | 메시지 `FOR UPDATE` | 상태 + 멱등 키 + 성공 1회 부분 UNIQUE. **원본 행은 잠그지 않음**(INT-01) |
| 엑셀 확정 | 분석은 잠금 없이 → 반영 시 수업·평가·결과 `FOR UPDATE` | 버전 없이 덮어씀(H2 정책) |

**흐름별 부분 저장 가능성**

| 흐름 | 결론 |
|---|---|
| 1. 학생 등록 + 수강 | 한 트랜잭션(flush → 감사 → commit). 수강 실패 시 학생도 저장 안 됨(B-1 테스트) |
| 2. Excel Preview → Confirm | 미리보기는 쓰기 없음. 확정은 **데이터 전체가 한 트랜잭션**(중간 실패 시 전부 롤백, B-1 테스트). 안내 초안은 commit **후** 100건 단위 별도 트랜잭션 → 초안 일부 실패는 결과의 `skipped`로 보고됨(의도된 설계). 단, 초안 단계의 예상 밖 예외는 500이 되어 "저장됨"을 알리지 못함(INT-I4) |
| 3. 수업 생성·수정·취소 | 한 트랜잭션. 동시 생성은 UNIQUE + `start_today_lesson`의 재조회로 처리 |
| 4. 출결·성적 | 요청 전체가 한 트랜잭션. 항목 하나라도 충돌하면 전체 409 |
| 5. 생성 → 확정 → 첫 발송 | 단계마다 독립 트랜잭션. 발송은 상태 변경 + 시도 기록 + 감사를 같은 commit. Mock Sender는 **트랜잭션 안에서** 호출됨(현재는 프로세스 내 함수라 무해, INT-I1) |
| 6. 실패 → 재시도 | 같은 규칙 + 멱등 키 재생 |
| 7. 직원·배정 변경 + 감사 | 같은 트랜잭션(11-2-B-1에서 보완, 롤백 테스트 있음) |

## 4. TOCTOU 분석 및 재현 결과 (Stage 2)

### 4.1 호출 경로와 시점
`POST /notifications/{id}/mock-send`(재시도·일괄 발송 동일)의 순서는 다음과 같다(`notifications/service.py`).
1. `_locked_for_send` — 메시지 행 `FOR UPDATE`, 멱등 키 확인(726-739)
2. 상태 확인(745 / 773)
3. **`_reject_changed_source` → `source_changed`**(750-761, 408-419) — 수업·출결·연결 평가·결과·보호자 이메일·수강 대상 여부를 다시 읽어 렌더링 지문(`source_hash`)을 비교. **잠금 없는 READ COMMITTED 조회**
4. `_deliver` — 시도 번호 조회 → `MockSender.send()` → 시도 행 INSERT·상태 UPDATE → 감사 INSERT → **commit**(783-823)

원본을 바꾸는 쓰기(4절 표의 출결·성적·수업·평가·연락처·휴원·엑셀)는 **메시지 행을 잠그지 않는다.** 발송 트랜잭션도 원본 행을 잠그지 않는다. 따라서 3단계 직후부터 commit까지 끼어든 원본 변경은 서로를 막지 않는다.

### 4.2 재현(R1) — **재현됨**
`scratchpad\p113\test_p113_integrity_repro.py::test_r1_…`. 3단계 직후에 대기 지점을 넣고(운영 코드 무변경, 이 프로세스에서만 패치) 다른 직원의 출결 저장을 실행했다.
- 선생님의 출결 저장(PRESENT→ABSENT)은 **0.23초 만에 200**으로 끝났다. 진행 중인 발송이 막지 않았다.
- 이어서 발송이 commit되었다. 메시지는 `MOCK_SENT`, 본문은 "출결: 출석", DB 출결은 `ABSENT`다.
- 감사 순서는 `ATTENDANCE_UPDATED` → `NOTIFICATION_MOCK_SEND`(변경이 먼저 확정된 뒤 발송 기록). 새 세션으로 다시 검사하면 `source_changed = True`.

**자연 발생 창 측정**(대기 지점 없이, `test_p113_window.py`): 원본 검사 종료부터 commit까지 발송 20건에서 **중앙값 19.5ms, 최소 15.3ms, 최대 28.6ms**(로컬). 같은 학생의 원본이 이 수십 ms 안에 바뀌어야 발생한다.

### 4.3 기존 보호의 범위(반박 검토)
- 확정(approve)에도 같은 창이 있지만, **발송이 다시 검사하므로** 낡은 확정은 발송 단계에서 `SOURCE_CHANGED`로 막힌다 → 문제 없음.
- 변경이 3단계 **전에** commit되면 READ COMMITTED 조회가 그 변경을 보고 409로 막는다(기존 테스트 `test_confirmed_message_is_not_sent_after_its_attendance_changed`).
- 메시지 행 잠금은 메시지끼리만 직렬화한다. 원본 쓰기와는 교차한다 → **창 안의 변경은 보호되지 않는다.** 결함으로 확정한다.

### 4.4 대안 비교

| 대안 | 정합성 보장 범위 | 복잡도 | 데드락 위험 | 회귀 영향 | DB 부하 |
|---|---|---|---|---|---|
| A. 트랜잭션 경계 조정(검사를 commit 직전으로) | 창을 줄일 뿐 0이 아님 | 낮음 | 없음 | 낮음 | 없음 |

| F. 발송·원본 쓰기 모두 SERIALIZABLE | 이론상 완전. 모든 쓰기 경로 재시도 로직 필요 | 높음 | 직렬화 실패 재시도 | 큼 | 중간 |

**R5 — 잠금 효과 실측**(`test_r5_…`, 운영 코드 무변경. 별도 연결로 잠금을 잡고 실제 API 쓰기가 기다리는지 측정):

| 보유한 잠금 | 대상 쓰기 | 기다림 |
|---|---|---|
| 수업 `FOR SHARE` | 출결 저장 | **아니오**(출결도 SHARE라 충돌 없음) |
| 수업 `FOR UPDATE` | 출결 저장 | 예 |
| 수업 `FOR UPDATE` | 수업에 연결된 평가 신규 생성(FK 검사) | 예 |
| 평가 `FOR SHARE` | 성적 저장 | **아니오** |
| 평가 `FOR UPDATE` | 성적 저장 | 예 |
| 학생 `FOR SHARE` | 연락처 수정 | 예 |

→ "원본 행을 `FOR SHARE`로 잠근다"는 단순한 방법은 **출결·성적에 효과가 없다.** 수업·연결 평가는 `FOR UPDATE`, 수강·학생·반은 `FOR SHARE`가 필요하다.

**권장: B.** `_reject_changed_source`에서 검사 **전에** 다음 순서로 잠근다.
1. 반 `FOR SHARE`(반 이름 변수)
2. 수업 `FOR UPDATE`
3. 연결 평가 `FOR UPDATE`(id 순)
4. 수강 `FOR SHARE`(휴원)
5. 학생 `FOR SHARE`(연락처)

- **데드락 검토**:
  - 원본 쓰기 경로는 메시지 행을 잠그지 않는다. 그래서 메시지 → 원본 순서와의 순환이 없다.
  - 엑셀 확정(수업→평가→수강)과 기록 수정(수업→평가)은 같은 방향이다.
  - 성적 저장(평가만)·휴원(수강만)·연락처(학생만)는 한 종류만 잠근다.
  - 같은 수업의 발송끼리는 수업 잠금에서 차례를 기다린다(일괄 발송은 원래 순차 처리).
- **부하**: 발송 1건당 행 잠금 5~6개, 대기는 최대 발송 1건(수십 ms).

### 4.5 현행 Mock 환경과 실제 발송의 구분
- **현행 Mock**: 보장 목표는 "`MOCK_SENT`로 기록된 본문은 기록 시점의 원본과 일치한다"이다. 대안 B로 충족된다. 실제 수신자가 없으므로 현재 피해는 기록 정합성(감사·화면)에 한정된다 → Medium.
- **실제 발송(향후)**: 외부 I/O를 DB 트랜잭션·행 잠금 안에서 하면 안 된다.
  1. 잠금 아래에서 원본을 검사하고 `SENDING`으로 기록한 뒤 commit한다(아웃박스).
  2. 트랜잭션 밖에서 발송하고 결과를 기록한다.
  - 보장 범위는 "발송 결정 시점의 원본과 일치"까지다. 발송 이후의 원본 변경은 '정정 안내' 정책으로 다뤄야 한다.
  - 상태 값이 추가되므로 스키마 변경 승인이 필요하다(INT-I1).

## 7. Alembic·DB 스키마 검증 (Stage 5)
- **Revision 체인**: 001 → 011 단일 선형. `alembic heads` = `011_staff_deleted_status`. 테스트 DB `alembic current` = head.
- **모델 ↔ 테스트 DB 차이**: `alembic check`(읽기 전용 autogenerate 비교) → **"No new upgrade operations detected"**. 비교 대상은 테이블·컬럼·타입·인덱스·UNIQUE·FK다.
- **`alembic check`가 비교하지 않는 것**: CHECK·트리거·EXCLUDE·FK 동작. 카탈로그에서 직접 확인했다(2절 이후 표, `.dev-data\tmp\catalog.txt`).
  - 버전 트리거 6개 테이블, 반 일치·휴원 동기화 트리거, EXCLUDE 1개
  - FK 동작: 업무 데이터 RESTRICT, 배정·세션 CASCADE, 행위자 SET NULL, 결과→평가 `ON UPDATE CASCADE`
  - 모두 마이그레이션 코드와 일치한다.
- **재현성**: 오프라인 SQL 생성(`--sql`)은 지원되지 않는다. 001이 Java 기준 DDL을 실행하고, 010·011은 데이터 건수를 확인한 뒤 진행하므로 실제 DB가 필요하다(설계상 의도, 결함 아님).
  - 기존 테스트가 테스트 DB에서 downgrade(→005/007/009)와 upgrade head를 반복 검증한다(오늘 통과, 이번에는 미실행).
  - **빈 DB에서 001부터 전체를 재구성하는 검증은 하지 않았다**(새 DB 생성 승인 필요).
- **롤백 정책**: 010·011 downgrade는 데이터가 있으면 진행하지 않는다(데이터 무손실 우선). 007 downgrade도 EXCUSED·2교시 데이터가 있으면 실패하도록 작성됨(주석). 운영·개발 DB에는 Migration을 실행하지 않았다.

## 8. 발견된 문제와 심각도

### INT-01 [Medium] 발송의 원본 검사와 commit 사이 TOCTOU — **재현됨**
- **위치**: `notifications/service.py` `mock_send`(741-748), `retry_mock_send`(763-781), `_reject_changed_source`(750-761), `source_changed`(408-411), `_deliver`(783-823). 조회는 `notifications/repository.py` `lesson`/`roster`/`linked_grades`(39-93)이며 잠금이 없다.
- **불변조건**: `MOCK_SENT`로 기록된 메시지 본문은 기록 시점의 원본(출결·성적·수업·연락처·수강 대상)과 일치한다.
- **실행 순서**: 발송 T1이 원본 검사(통과) → 쓰기 T2가 원본 변경 후 commit(잠금 충돌 없음) → T1이 commit(`MOCK_SENT`).
- **재현**: R1(강제 순서), 자연 창 15~29ms 실측.
- **현재 보호**: 메시지 행 잠금(메시지끼리만), 검사 전 commit된 변경은 감지.
- **최소 수정**: 대안 B(4.4). `_reject_changed_source` 안에서 원본 행 잠금 5종을 고정 순서로 건 다음 검사한다.
- **선택 근거**: 신규 행 삽입까지 막는 유일한 저비용 방법이다(R5). C·D는 창을 줄이거나 삽입을 놓친다.
- **회귀 위험**: 낮음. 같은 수업의 출결·성적 저장이 발송 1건 동안 대기한다.
- **우선순위**: 2

### INT-03 [Low] 평가 생성·수정이 연결 수업을 잠그지 않음 — **재현됨**
- **위치**: `academics/service.py` `_check_lesson_link`(397-405, `repo.lesson()` 잠금 없음), `create_assessment`(407-422), `update_assessment`(453-454). 상대 경로는 `update_lesson`(280-316, 수업 `FOR UPDATE` + `lesson_has_records`).
- **불변조건**: 취소된 수업에는 평가가 연결되지 않는다(취소는 기록 없는 수업만 가능).
- **실행 순서**: 평가 생성이 수업 확인(취소 아님) → 수업 취소가 기록 없음을 확인하고 commit → 평가 INSERT. FK 검사의 `KEY SHARE`는 취소 commit 뒤에 통과한다.
- **재현**: R4. 취소 200, 생성 201, 결과 (`CANCELLED`, 평가 1).
- **영향**: 취소 수업에 성적 입력 화면이 생긴다. 메시지는 렌더링 단계에서 '취소된 수업'으로 막힌다. 수업을 다시 '완료'로 바꾸면 복구된다.
- **최소 수정**: `_check_lesson_link`에서 `self.repo.lesson(lesson_id, lock="share")`. 수업 `FOR UPDATE`(취소)와 충돌하므로 어느 쪽이 먼저든 둘 중 하나가 정확히 거부된다(R5로 잠금 충돌 확인). 1줄.
- **회귀 위험**: 매우 낮음.
- **우선순위**: 1

### INT-04 [Low] 같은 엑셀 확정의 이중 제출 시 오해를 부르는 409 — **재현됨**
- **위치**: `lesson_upload/service.py` `confirm`(분석 → 반영), `_apply_block`(수업 잠금은 분석 **후**), 11-2-B-1에서 추가한 학생 키 위반 → `EXISTING_STUDENT_ELSEWHERE` 매핑.
- **실행 순서**: 두 요청이 모두 잠금 없이 분석('신규' 학생 = 충돌 없음) → 첫 요청이 수업 잠금·저장·commit → 둘째 요청이 낡은 분석으로 학생 INSERT → 키 위반 → 409 "같은 이름(·학교)의 학생이 이미 등록되어 있어…".
- **재현**: R3. 데이터는 정확하다(학생 1·수강 1·수업 1·결과 2).
- **영향**: 사용자가 "이미 저장됨"을 "다른 학생과 충돌"로 오해할 수 있다. 데이터 손상은 없다.
- **최소 수정(택1)**:
  - ① 반영 전에 반별 트랜잭션 advisory lock(`pg_advisory_xact_lock`, 스키마 변경 없음)을 정렬된 순서로 잡은 뒤 **잠금 아래에서 다시 분석**한다 → 늦은 요청은 '변경 없음'으로 200(멱등).
  - ② 409 문구에 "방금 같은 파일이 저장되었을 수 있습니다 — 다시 미리보기"를 추가한다.
  - 권장: ①(이중 클릭을 멱등으로).
- **우선순위**: 4

### INT-02 [Low · 잠재] 일괄 처리에서 원본 재검사가 객체 수명에 의존 — 현 코드 **미재현**
- **위치**: `notifications/repository.py` `linked_grades`(76-93)는 `populate_existing`이 없고, 세션은 `expire_on_commit=False`이다. `lesson`·`roster`는 `populate_existing`을 쓴다.
- **근거**:
  - R2: 일괄 발송 중 만점 변경 → 둘째 메시지가 정상적으로 `SOURCE_CHANGED`. SQLAlchemy 식별 맵이 객체를 **약하게 참조**해, 첫 메시지 처리 후 평가 객체가 해제되고 다시 읽히기 때문이다.
  - R2b: 평가 객체를 계속 참조하게 만들면(향후 캐싱·eager loading 같은 변경) 둘째 메시지가 **낡은 만점으로 발송**된다.
- **최소 수정**: `linked_grades`의 두 조회에 `execution_options(populate_existing=True)`(같은 파일 다른 조회와 동일 규칙). 2줄.
- **우선순위**: 3(INT-01 수정과 함께)

### Informational
- **INT-I1 실제 발송 전환 시**: `_deliver`가 발송 I/O를 트랜잭션·메시지 행 잠금 안에서 수행한다. 실제 발송에서 발송 성공 후 commit이 실패하면 기록 없이 발송된 상태가 되고, 재시도하면 이중 발송이 된다. 아웃박스(`SENDING` 상태) 설계가 필요하다(상태 CHECK 변경 → 스키마 승인).
- **INT-I2 권한 회수와 진행 중 요청**: 권한은 요청 시작 시 검사한다. 회수 commit이 진행 중인 요청과 겹치면 그 요청은 완료된다(수 ms). 일반적인 수준이다.
- **INT-I3 버전 없는 관리 데이터**: 연락처·반 이름/운영·직원 이름은 마지막 저장이 우선한다(행 잠금으로 직렬화되지만 충돌을 알리지 않음). 관리자 전용·빈도 낮음. 연락처 변경은 메시지 발송 단계에서 감지된다.
- **INT-I4 업로드 확정 후 초안 단계 예외**: `_drafts`는 `CompatibilityError`만 잡는다. 예상 밖 예외면 데이터는 저장되었는데 응답은 500이다. 재업로드해도 변경 없는 행은 건너뛰므로 안전하지만, 사용자가 상태를 오해할 수 있다.
- **INT-I5 발송 요청에 버전 없음**: 화면이 본 뒤 다른 직원이 확정 취소 → 수정 → 재확정하면, 처음 화면에서 누른 발송이 새 본문을 보낸다. 새 본문도 권한자가 확정한 것이라 정책상 허용 범위다.
- **INT-I6 미리보기 이후 앱 수정값**: 확정은 미리보기 이후 앱에서 고친 점수도 엑셀 값으로 덮어쓴다(H2 정책). 감사에 이전→이후가 남는다. 정책 변경 대상 아님.
- (참고) 분석·처리 현황 화면은 READ COMMITTED에서 여러 조회로 계산하므로, 동시 쓰기 중에는 합계가 순간적으로 어긋날 수 있다(읽기 전용, 새로고침으로 해소).

## 10. 기존 설계에서 유지할 장점
- **DB가 최종 심판**: 업무 키·수업·결과·활성 메시지·성공 1회·멱등 키·휴원 중복을 모두 DB 제약이 막아, 앱 검사가 경쟁에서 져도 중복이 저장되지 않는다(R3·R4에서도 중복은 0).
- **트리거 기반 버전**: 모든 UPDATE 경로(엑셀 덮어쓰기 포함)에서 버전이 올라가 낙관적 검사가 우회되지 않는다.
- **복합 FK로 반 일관성**, 만점 변경의 `ON UPDATE CASCADE` + CHECK 조합.
- **요청 = 트랜잭션**, 업무와 감사가 같은 commit, `_abort`에서 rollback 후 응답(잠금 즉시 해제).
- **메시지 상태 변경은 행 잠금 + 버전 + 상태 검사**, 발송은 잠금 후 멱등 키 확인.
- 일괄 처리는 메시지마다 독립 트랜잭션이라, 한 건의 실패가 나머지를 되돌리지 않는다.

## 11. 검증하지 못한 영역·승인 필요 사항
- **기존 통합 테스트 재실행**: 파괴적 초기화(TRUNCATE·downgrade) 때문에 이번에는 하지 않았다. 마지막 전체 결과는 오늘 Phase 11-2-B-2 후속에서 백엔드 181건 통과다. → **재실행 승인 필요**(승인되면 남은 P113 재현 데이터도 함께 정리됨)
- **빈 DB에서 001→011 전체 재구성**: 테스트 컨테이너에 임시 DB를 만들어야 한다 → 승인 필요
- **개발 DB의 Revision·불변조건 점검**: 개발 DB에는 접속하지 않았다. 8절 I1~I6 점검 쿼리를 읽기 전용으로 실행할지는 사용자 결정
- 운영 규모 부하, 실제 네트워크 지연을 가정한 창 크기, 다중 프로세스(워커 2개 이상) 상호작용
- Java 레거시 경로의 쓰기(트리거로 버전·휴원은 보호됨)
- 프론트엔드의 이중 제출 방지(버튼 비활성) 동작
