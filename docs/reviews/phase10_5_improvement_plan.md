## 2. 유지할 기존 설계와 장점
1. **DB 제약 우선 무결성**: 성적 행의 만점 복제 복합 FK + `score ≤ max_score`(`tables.py:240-257`), 휴원 겹침 EXCLUDE, 학생·반 수강 1건 UNIQUE, 활성 메시지·성공 발송 부분 UNIQUE, `version` 트리거(`alembic/versions/006…:20`, `008…:49`). — 손대지 않는다.
2. **변경 + 감사 = 한 트랜잭션**, 행 잠금 + 버전 + 멱등 키(`notifications/service.py:576-592`).
3. **단일 규칙 소스**: `eligible_on`, `can_access_classroom`을 모든 모듈이 공유.
4. **비순환 모듈 의존**: `auth ← learningops ← academics ← notifications ← {lesson_upload, message_operations}`, `analytics → academics`.
5. **인증·인가 기본기와 IDOR 방어**(위 표), 개인정보 응답 필드의 역할별 제외.
6. **격리 테스트 DB 안전장치**와 실제 PostgreSQL 통합 테스트.
7. **과잉 설계 없음** — 추가 계층·패턴·라이브러리를 권하지 않는다.

## 3. 반드시 수정 (A)

### A-1 확정된 메시지도 원본이 바뀌면 발송을 막고 화면에 알린다
- **필요성**: 학부모에게 사실과 다른 출결·성적이 나간다(재현됨). 같은 규칙이 재시도에는 있어 경로별로 불변식이 다르다.
- **파일**: `backend/app/modules/notifications/service.py`(`mock_send`, `_detail`), `frontend/src/features/notifications/ReviewTab.tsx`(경고 문구·버튼)
- **해결**: ① `mock_send`에서 상태 확인 뒤 `retry_mock_send`와 같은 `source_changed` 검사 → 409 `SOURCE_CHANGED`(기존 코드·문구 재사용). ② `_detail`의 `check_source`를 `APPROVED`, `MOCK_FAILED`까지 확장. ③ 화면: 원본 변경이면 '모의 발송'·'재시도' 비활성 + 상태별 안내("확정 취소 후 취소·재생성"). 확정 무효화 트리거·새 상태는 만들지 않는다(현재 검사 방식 유지).
- **영향 범위**: 메시지 확정 후 원본이 바뀐 건만. API 계약 불변(기존 오류 코드), DB 변경 없음.
- **테스트**: 백엔드 통합 — 확정 → 출결 수정 → 상세 `source_changed: true` → `mock-send` 409, 시도 행 0건, 상태 APPROVED 유지; 원본 그대로면 기존처럼 200(회귀). 프론트 — APPROVED + 원본 변경 시 발송 버튼 비활성.
- **완료 기준**: 위 테스트 통과 + Phase 8·9 메시지 통합 테스트 전부 통과 + 1차 재현 시나리오가 409로 끝남.
- **우선순위**: 1 (선행 없음)

## 4. 수정 권장 (B)

### B-1 반별 학생 목록을 끝까지 받는다
- **필요성**: 51명 이상 반에서 학생이 화면에서 조용히 빠짐(학생 관리, 성적 분석 학생 선택).
- **파일**: `frontend/src/features/learningops/api.ts`(`students`)
- **해결**: `limit=100`으로 받고 받은 수가 limit와 같으면 `offset`을 늘려 다음 페이지를 이어 받는 작은 반복(호출부·백엔드·API 계약 변경 없음).
- **테스트**: 함수 단위 테스트(100명 + 3명 응답 → 103명, 요청 2회), 기존 `LearningOpsPage`·`AnalyticsPage` 테스트 회귀.
- **완료 기준**: 단위 테스트 통과, 기존 테스트 기대값 변경 없음. **우선순위**: 2 (독립)

### B-2 "진행된 수업" 규칙을 한 곳에서 정의한다
- **필요성**: 핵심 업무 규칙의 이중 구현(R1). 두 화면이 같은 정의라는 문서 약속을 코드가 보장하지 않음.
- **파일**: `backend/app/modules/analytics/repository.py`(`held_lesson`) → `backend/app/modules/academics/repository.py`(`eligible_on` 옆)로 이동, `backend/app/modules/message_operations/{repository,service}.py`가 같은 식을 사용(수업 조회에 `held` 열 추가, `service.py:126`의 Python 판정 대체).
- **영향 범위**: 처리 현황 계산 경로. 결과는 현재와 같아야 함(동작 변경 없는 리팩터링). API·DB 불변.
- **테스트**: Phase 9 처리 현황 통합 테스트·Phase 10 분석 테스트 전부 기대값 그대로 통과. 필요 시 "지난 SCHEDULED + 출결 1건 = 진행" 사례가 두 API에서 같은지 확인하는 테스트 1건.
- **완료 기준**: 규칙 정의가 1곳, 기존 테스트 무변경 통과. **우선순위**: 3 (A-1과 독립, 마지막에)

### B-3 엑셀 재업로드가 바꾸는 값을 미리 보여 주고 기록한다 (사용자 결정 2026-11-20)
- **필요성**: 앱에서 고친 점수·등급이 재업로드로 되돌아가도 미리보기·결과·감사 어디에도 드러나지 않음. 저장 규칙(엑셀이 점수의 출처)은 **바꾸지 않는다**.
- **검증된 덮어쓰기 범위**(`lesson_upload/service.py`): 엑셀 칸에 값이 있고 앱 값과 다른 점수(`:468-469`)·예습/주간 등급(`:437-440`), 결석·인정결석 학생의 빈 점수 → 미응시(`:445-447`, 앱 점수가 있어도), 평가 만점(`:332-333`). 출석 학생의 빈 칸은 앱 값 유지.
- **파일**: `backend/app/modules/lesson_upload/{service,schemas}.py`(미리보기 비교·감사 상세), `frontend/src/features/notifications/{uploadApi.ts,UploadTab.tsx}`
- **해결**: ① 미리보기 행에 `app_changes`(항목·앱 값·엑셀 값) 추가 — 기존 `app_attendance` 계산과 같은 조회 재사용, **필드 추가만**(기존 필드·확정 동작 불변). ② 화면: 검증 요약의 '확인 필요'에 "앱 값과 다른 점수·등급 n건" 포함, 행에 "앱 9 → 엑셀 8" 표시, 확정 확인창에 건수. ③ `UPLOAD_ROW_APPLIED` 감사에 바뀐 항목의 이전→이후. ④ 만점을 기존 점수보다 낮추려다 DB가 거부하면 "동시에 저장" 대신 "만점보다 큰 기존 점수가 있습니다" 안내(코드 확인: CHECK 위반이 `IntegrityError`로 같은 409 문구로 나감 — 실행 재현은 안 함). ⑤ M2: `learningops/router.py:300` 주석을 "학생 목록에서는 관리자만, 메시지 상세는 발송 확인용(2026-11-18 결정)"으로 정리.
- **영향 범위**: 업로드 미리보기 응답(추가 필드), 업로드 화면, 감사 상세. DB 스키마·확정 규칙·다른 API 불변.
- **테스트**: 통합 — 앱에서 점수 정정 → 같은 파일 미리보기에 차이 1건(앱 9, 엑셀 8) → 확정 후 감사에 이전 9·이후 8; 차이 없으면 `app_changes` 비어 있음; 결석 학생 빈칸이 앱 점수를 미응시로 바꾸는 경우 표시; 만점 낮춤 거부 시 새 안내 코드. 프론트 — 확인 필요 건수·행 표시. 기존 업로드 테스트 기대값 유지.
- **완료 기준**: 위 테스트 통과 + 기존 업로드·파서 테스트 무변경 통과. **우선순위**: 2 (A-1 다음, B-1·B-2와 독립)
