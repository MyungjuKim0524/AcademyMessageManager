## 0. 환경과 측정 방법
- **환경**: 작업 시작 시 Docker Desktop이 꺼져 있었다.
  - Docker Desktop을 켠 뒤 **격리 테스트 컨테이너만** 시작했다(`docker start academy-learningops-postgres-test`).
  - `run-postgres-integration.ps1` 검사 블록(라벨 `isolated-test`/`allowed`, `127.0.0.1:55432`, DB·사용자)을 통과했다. PostgreSQL 17.6, revision 011, 시작 시 데이터 0건.
  - 개발 DB 컨테이너와 `academy-postgres`는 **꺼진 상태 그대로**이며 접근하지 않았다. 데몬을 시작해도 자동으로 켜지지 않음을 확인했다.
- **측정 도구**(저장소 밖, scratchpad `p114\`):
  - 앱 엔진에 `before_cursor_execute` 이벤트를 걸어 요청당 SQL 문 수를 센다.
  - 같은 형태의 반을 두 규모로 만들었다. 소형은 학생 10명·수업 6회, 대형은 학생 40명·수업 24회이며, 수업마다 연결 평가와 점수, 전원 출결이 있다.
  - 데이터는 `P114` 접두사의 가상 행을 INSERT로만 넣었다. TRUNCATE·DELETE는 하지 않았다.
- **수치의 성격**: 시간은 로컬(Windows + Docker/WSL2) 측정값이다.
  - 조회는 3회 중앙값, 쓰기는 수정 전 1회·수정 후 3회 중앙값이다.
  - 쓰기 시간은 실행마다 ±30% 흔들린다. **SQL 문 수가 비교 기준으로 더 신뢰할 만하다.**

## 1. 성능 및 예외 처리 기준선

### 1.1 조회·쓰기(대형 규모, 수정 전)
| 경로 | SQL 문 수 (10명 → 40명) | 시간(40명) | 판단 |
|---|---|---|---|
| 반·학생·수업·출결·성적·평가 목록, 학생 기록 | 2~6, **규모와 무관** | 30~64ms | 정상(N+1 없음) |
| 분석(출결·성적·관심 학생·학생 리포트) | 4~13, 규모와 무관 | 50~180ms | 정상 |
| 메시지 목록·상세·일괄 화면, 운영 현황(담당 반) | 4~13, 규모와 무관 | 47~102ms | 정상 |
| 출결·성적 일괄 저장, 초안 일괄 생성 | 12~16, 규모와 무관 | 112~136ms | 정상 |
| **진도표 `/classrooms/{id}/progress`** | 14 → **32**(수업일마다 +1) | 274ms (응답 212KB) | 수업일별 조회. 측정 결과 **요청 시간의 60%**(162~193ms) |
| **일괄 확정 `batch-approve`** | 225 → **885**(메시지당 22) | 4,126ms | 아래 분석 |
| **일괄 모의 발송 `batch-mock-send`** | 275 → **1,085**(메시지당 27) | 4,535ms | 아래 분석 |
| 엑셀 확정 | 65 → 215(행당 약 5) | 835ms | 행 잠금·쓰기는 설계상 필요(11-3-B) |

**일괄 처리 분석**: 메시지 1건과 2건 배치의 SQL을 기록해 메시지당 차이를 쟀다.
- 확정은 22문장 중 약 11문장이, 발송은 27문장 중 약 11문장이 **배치 응답이 쓰지 않는 상세 화면 구성**(`_detail`)이었다.
  - 대상: 다시 읽기, 목록 조인, 시도·이력·직원 이름 조회, **두 번째 원본 검사**
- 배치 응답에는 결과 상태와 오류 코드만 들어간다.

**관리자 운영 현황**(전체 반, 60일, 수업×학생 4,914행)은 SQL 7문장으로 일정하다. 따뜻한 상태에서 526ms였다.
- 내역: SQL 약 185ms, Python 집계 루프·ORM 속성 접근 약 390ms(cProfile).
- 데이터에 비례해 늘지만 배포 차단 요인은 아니다 → P2 유지(8절).
- 최초 측정치 2.4초는 대량 시드 직후의 첫 호출(콜드) 값이라 판단 근거로 쓰지 않았다.

## 5. 예외 처리 개선 내용
| 상황 | 수정 후 응답 | 확인 방법 |
|---|---|---|
| DB 연결 불가·인증 실패·연결 수 초과·서버 종료, 풀 대기 초과 | **503 `DATABASE_UNAVAILABLE`** "데이터베이스에 연결할 수 없습니다. 잠시 후 다시 시도해주세요." | 실제 연결 실패 통합 테스트, 분류표 단위 테스트 |
| 데드락·직렬화 실패·잠금 시간 초과 | **409 `TRANSACTION_CONFLICT`** "다른 작업과 동시에 처리되어 저장하지 않았습니다. 잠시 후 다시 시도해주세요." | 실제 잠금 시간 초과(발송) 통합 테스트, 분류표 |
| 프로그래밍·데이터 오류(42P01, 22012, 무결성 위반 미처리분 등) | 기존 **500 `INTERNAL_ERROR`** 유지(버그를 재시도로 가리지 않음) | 분류표 |
| 연결 대기 | 최대 5초 후 실패 → 503 | 실제 연결의 libpq 파라미터 `connect_timeout=5` |

- **오류 계약**: 응답 형식 `{code, message, fields}`는 같다.
  - `DATABASE_UNAVAILABLE`(503)은 기존 코드를 재사용했다.
  - `TRANSACTION_CONFLICT`(409)는 **새 오류 코드(추가)**다.
  - 프론트엔드는 서버의 `code`·`message`를 그대로 표시하므로(`ApiClientError.ts`) 화면 변경 없이 동작한다.
- **정리**: 분류는 이미 롤백된 뒤(`get_db`)의 응답 단계에서만 일어난다. 예외를 삼키지 않으며, 모든 경우에 정제된 오류 로그(유형·SQLSTATE·요청 ID, 예외 문구 없음, 11-2-B-2)를 그대로 남긴다.
- 요청 로그의 `status`도 실제 응답 코드로 기록된다(테스트로 확인).

## 7. 기존 트랜잭션·보안 구조에 미친 영향
- **트랜잭션·잠금**: 바꾸지 않았다.
  - 일괄 처리는 여전히 메시지마다 독립 트랜잭션이고 행 잠금·버전·원본 잠금(11-3-B)·원본 검사·멱등 키·감사를 모두 거친다. 생략한 것은 commit **이후**의 화면용 재조회뿐이다.
  - 11-3-B 동시성 테스트 23건이 통과했다.
- **진도표**: 판정 규칙(`eligible_on`)은 그대로이고 실행 방식만 바뀌었다. 여섯 가지 수강 형태로 이전 구현과 **결과 집합·API 응답 전체가 같음**을 테스트로 고정했다.
- **보안**: 인증·RBAC·CSRF는 바꾸지 않았다. 오류 문구에 내부 정보·SQL·개인정보가 없고 로그도 정제된다(테스트로 확인). 버퍼링 개선으로 인증 전 CPU 소모가 줄었다.

| 앱 차원의 statement_timeout·요청 타임아웃 | 긴 쿼리가 측정되지 않음. 배포 프록시·DB 측 설정과 함께 정할 사항 |

## 9. 남은 위험
- ~~기존 TRUNCATE 기반 통합 테스트 미실행~~ → 사용자 승인 후 전체 회귀를 실행해 **131건 모두 통과**했다(6절).
  - 500을 기대하는 기존 테스트(SQLAlchemyError, IntegrityError, 감사 강제 실패 DataError 22001)도 재분류 대상이 아니어서 그대로 통과했다.
- 측정은 로컬 머신 값이다. 무료 배포 환경(낮은 CPU, 원격 DB 왕복 지연)에서는 일괄 처리가 더 느려질 수 있다. 줄인 쿼리 수가 그만큼 지연을 덜어 준다.
- 연결 풀 10개(5 + overflow 5)와 스레드풀 40의 조합에서, 동시 DB 요청이 10을 넘으면 최대 10초 대기 후 503이 된다. 배포 환경의 DB 연결 한도와 함께 11-5에서 확인할 사항이다.
- 재현 데이터 `P114`·`P114E` 가상 행은 승인된 전체 회귀의 TRUNCATE로 정리되었다(실행 전 반 108·직원 214·감사 1,905행 → 실행 후 0).
- Docker Desktop과 테스트 컨테이너는 켜진 상태로 두었다.

## 10. 최종 판정 — **PASS** (2026-11-21, 전체 회귀 후 CONDITIONAL PASS에서 갱신)
- 측정으로 확인된 P1 5건(일괄 처리 쿼리 증폭, 인증 전 업로드 버퍼링, DB 장애·잠금 충돌의 500 응답, 연결 무한 대기)과 효과가 명확한 P2 1건(진도표)을 최소 수정으로 해결했다.
