  - 취소가 먼저인 경우: 생성은 FK 검사에서만 잠깐 기다린 뒤 취소된 수업에 201
- **수정**: `academics/service.py:401` — `self.repo.lesson(lesson_id, lock="share")`.
  - 출결 쓰기가 이미 쓰는 잠금과 같다.
  - 같은 함수를 쓰는 `update_assessment`의 수업 연결 변경에도 함께 적용된다.
- **동작**:
  - 생성이 먼저 잠금을 잡으면, 취소(`FOR UPDATE`)가 기다린 뒤 평가를 보고 **409 `LESSON_HAS_RECORDS`**(기존 정책)
  - 취소가 먼저면, 생성이 기다린 뒤 다시 읽어 `CANCELLED`를 보고 **400 `INVALID_LESSON_LINK`**
  - 실패 시 평가·감사 모두 저장되지 않음
- **업무 정책 확인**: "평가가 먼저 확정됐다면 이후 취소는 거부"는 기존 `LESSON_HAS_RECORDS` 규칙 그대로다. 정책은 바꾸지 않았다.
- **잠금 순서 검토**: `update_assessment`는 평가 → 수업(SHARE) 순서로 잠근다. 반대 순서(수업 → 평가)를 쓰는 경로(엑셀 확정, 발송)는 **그 수업에 이미 연결된 평가만** 잠그고, 연결을 바꾸는 평가는 아직 그 수업 소속이 아니다. 그래서 같은 쌍에서 순환이 생기지 않는다(8절).

### 4.2 수정
- `notifications/repository.py:112` `lock_sources(row)`: 다음 순서로 잠근다.
  1. 반 `FOR SHARE`
  2. 수업 `FOR UPDATE`
  3. 연결 평가 `FOR UPDATE`(id 순)
  4. 수강 `FOR SHARE`
  5. 학생 `FOR SHARE`
  - 모든 조회에 `populate_existing`을 붙여 잠금 후 최신 행으로 ORM 객체를 갱신한다.
- `notifications/service.py:759` `_reject_changed_source`: 원본 검사 **직전에** `lock_sources` 호출.
  - 첫 발송·재시도·일괄 발송이 모두 이 함수를 지나므로 정책이 같다.
  - 잠금은 발송 commit(상태·시도 기록·감사 동시 저장, 기존 원자성 유지)까지 유지된다.
- 확정(approve)은 바꾸지 않았다. 확정 시점의 검사가 늦더라도 발송이 다시 잠그고 검사하므로, 원본과 다른 메시지는 성공 기록이 남지 않는다.

### 4.3 잠금 설계 검증(지시된 질문별)
- **`FOR UPDATE`가 막는 것**:
  - 그 행의 UPDATE·DELETE와 다른 트랜잭션의 `FOR UPDATE / NO KEY UPDATE / SHARE / KEY SHARE` 잠금
  - 그 행을 **참조하는 행의 INSERT 및 FK 열 UPDATE**. PostgreSQL FK 검사는 부모 행에 `FOR KEY SHARE`를 잡는데, 이 잠금은 `FOR UPDATE`와만 충돌하고 `FOR NO KEY UPDATE`와는 충돌하지 않는다. 그래서 수업·평가에는 `NO KEY UPDATE`가 아닌 `FOR UPDATE`를 썼다.
- **기존 행이 없을 때(신규 원본)**:
  - 새 출결 행: 쓰기 경로가 먼저 수업을 잠그고, FK 검사도 수업에 KEY SHARE를 잡는다 → 이중으로 차단
  - 새 점수 행: 평가 잠금 + FK(KEY SHARE on 평가)
  - 새 연결 평가: 수업 SHARE(INT-03) + FK(KEY SHARE on 수업)
  - **테스트로 확인**(`new_linked_test`)
- **일반화하지 않은 부분**: FK가 없는 관계는 FK 잠금에 기대지 않는다. 그런 관계(같은 수업의 기존 출결 행 값 변경 등)는 "쓰기 경로가 부모를 먼저 잠근다"는 코드상 규칙에 의존한다. 이 규칙이 없는 **앱 밖 쓰기(Java 레거시, 직접 SQL)는 기존 행 값 변경을 막지 못한다**(12절).
- **연락처**: 학생 `FOR SHARE` ↔ 연락처 수정 `FOR UPDATE` 충돌을 테스트로 확인(`contact`). 반대 순서에서는 발송이 대기 후 `SOURCE_CHANGED`(수신자가 지문에 포함).
- **여러 메시지·일괄 발송**: 메시지마다 독립 트랜잭션, 매번 같은 순서. 같은 수업의 발송끼리는 수업 잠금에서 차례대로 처리된다.
- **READ COMMITTED 재확인**:
  - 잠금 대기가 끝나면 PostgreSQL이 잠근 행의 최신 버전을 다시 읽는다.
  - 이후 원본 조회는 새 문장(새 스냅샷)이라 그 사이 commit된 변경이 보인다.
  - 반대 순서 테스트 2종(출결·성적)에서 발송이 대기 후 409를 반환했다.
- **Identity Map**: 잠금 조회 5종과 `lesson()`·`roster()`·(INT-02 후) `linked_grades()`가 모두 `populate_existing`이다. 같은 요청 앞부분에서 `db.get`으로 캐시된 반 객체도 잠금 조회가 최신 값으로 덮어쓴다.

### 4.4 성능·데드락
- **잠금 보유 시간**(잠금 시작 → 발송 commit, 실측): 단독 발송 6건 **중앙값 85.6ms, 최대 104.8ms**. 발송 + 같은 수업 출결 쓰기 동시 실행(벽시계) 중앙값 118ms, 최대 219ms. 로컬 측정치이며 환경에 따라 다르다.
- **대기 범위**: 같은 수업의 출결·성적·평가 쓰기, 같은 학생의 연락처, 같은 반의 이름 변경만 발송 1건 동안 기다린다. 다른 수업·반은 영향이 없다. 발송 건수가 늘어도 메시지마다 잠금을 풀고 다음으로 넘어가므로 잠금이 누적되지 않는다.
- **데드락**:
  - 원본 쓰기 경로는 어느 것도 메시지 행을 잠그지 않는다.
  - 엑셀 확정(수업 → 평가 → 수강)·기록 수정(수업 → 평가)은 발송과 같은 방향이다.
  - 성적(평가만)·휴원(수강만)·연락처(학생만)·반 수정(반만)은 한 종류만 잠근다 → 순환 없음.
  - 경합 테스트(발송 6 + 출결 6 동시)를 5회 반복해 500·데드락 0건을 확인했다.
  - 그래도 데드락이 나면 PostgreSQL이 한쪽을 중단시키고, 그 요청은 rollback 후 500이 된다(부분 저장 없음. 아래 실패 테스트와 같은 경로).
- **타임아웃·실패**:
  - 앱에 lock_timeout은 설정하지 않았다(기존 경로와 동일, 대기는 쓰기 1건 길이).
  - 테스트에서 300ms lock_timeout을 강제해 실패시키면 500이 나고 상태·시도·감사가 남지 않는다.
  - 감사 저장을 강제로 실패시켜도 시도 기록과 상태가 함께 롤백되고, 이후 정상 발송된다.

## 6. INT-04 Excel Confirm 멱등성 개선 결과
- **기존 계약 확인**:
  - 업로드 API에는 멱등성 키도 결과 저장 테이블도 없다.
  - 계약은 **내용 기반 멱등**이다: 같은 파일을 다시 확정하면 200, 앱과 같은 행은 '변경 없음'으로 건너뛰고 감사도 남기지 않는다.
  - 따라서 "동일 멱등성 키·다른 내용" 시나리오는 이 API에 해당하지 않는다. 대신 "다른 내용의 동시 확정"을 검증했다.
- **원인 재확인**:
  1. 분석은 잠금 없이 수행되고, 수업 잠금은 분석 후 반영 단계에서 잡힌다.
  2. 그래서 같은 파일 두 요청이 모두 '신규 학생'으로 분석된다.
  3. 늦은 요청은 이미 등록된 자기 학생에 대해 키 위반을 일으켜 409 `EXISTING_STUDENT_ELSEWHERE`가 됐다.
- **반별 잠금 후 재분석의 타당성**:
  - 학생 신규 등록·수강·수업 생성이 모두 반 단위 작업이라 반이 적절한 직렬화 단위다.
  - 행 잠금으로는 아직 없는 행(새 수업, 새 학생)을 잠글 수 없다. 그래서 트랜잭션 범위 advisory lock을 썼다(스키마 무관, commit/rollback 시 자동 해제).
- **수정**(`lesson_upload/service.py`):
  - `analyse`를 파싱과 `_match`(DB 대조)로 나눴다(197행).
  - `confirm`(467행)은 1차 분석으로 반 목록을 얻는다 → `_serialize_classes`(211행)가 반 id **정렬 순서**로 `pg_advisory_xact_lock(11303<<32 + 반 id)` → **잠금 아래에서 다시 `_match`** → 그 결과로 결정 확인과 쓰기를 진행한다.
  - 미리보기·응답 스키마는 그대로다.
- **결과**:
  - **동일 확정 동시 2회**: 둘째가 첫째 commit까지 대기 → 200(새 학생 0, 저장 0, 변경 없음 2). **순차 재전송과 같은 응답**(테스트로 비교)
  - **다른 내용 동시 2회**: 순서대로 둘 다 반영(둘째는 바뀐 1행만 저장, 기존 H2 덮어쓰기 규칙)
  - **실제 식별 충돌**(서로 다른 두 반이 같은 새 이름을 동시에 등록): 한쪽 200, 다른 쪽 **409 `EXISTING_STUDENT_ELSEWHERE` 유지**. 다른 반 학생을 재사용하지 않음(SEC-01). 실패한 쪽은 학생·수강·결과 모두 저장되지 않음
  - 다른 반 기존 학생 자동 재사용 차단·동명이인·학교 누락 정책: B-1 테스트 12건이 전체 회귀에서 통과
  - 중복 방지: 학생 1·수강 1·수업 1·결과 2, 업로드 수강 감사 1·반영 감사 1(중복 없음)
- **409를 200으로 바꿔 숨기지 않았다**: 학생 키 위반 → 409 매핑은 그대로다. 같은 반의 두 확정이 서로를 오인하지 않도록 순서만 정했다.
- **비용**: 확정 요청에서 DB 대조를 한 번 더 한다(파싱은 1회). 같은 반 확정끼리만 순차 처리된다.

## 8. 잠금 순서·트랜잭션 경계(수정 후)
```
발송/재시도   : 메시지 FOR UPDATE → 반 SHARE → 수업 UPDATE → 연결 평가 UPDATE(id순) → 수강 SHARE → 학생 SHARE → 검사 → 발송·기록·감사 → commit
엑셀 확정     : 반별 advisory(id순) → [재분석] → 수업 UPDATE → 평가 UPDATE → 수강 UPDATE(복귀) → 결과 → commit → (초안: 별도 트랜잭션)
출결 저장     : 수업 SHARE → 출결 행 UPDATE → commit
기록 수정     : 수업 SHARE → 출결 행 → 평가 SHARE → 결과 행 → commit
성적 저장     : 평가 SHARE → 결과 행 UPDATE → commit
평가 생성     : 수업 SHARE(신규) → INSERT → commit
평가 수정     : 평가 UPDATE → (연결 변경 시) 새 수업 SHARE → commit
수업 수정·취소 : 수업 UPDATE → 기록 유무 확인 → commit
휴원·복귀     : 수강 UPDATE → commit       연락처: 학생 UPDATE → commit       반 수정: 반 UPDATE → commit
```
- 공통 방향은 반 → 수업 → 평가 → 수강 → 학생이다.
- 예외인 평가 수정(평가 → 새 수업)이 잠그는 새 수업은, 그 평가를 아직 연결 평가로 보지 않으므로 순환이 생기지 않는다(3절).
- advisory lock은 엑셀 확정끼리만 쓰고 항상 가장 먼저 잡는다.

## 11. DB·API·보안 호환성
- **DB**: 스키마·제약·트리거·Migration 변경 없음. 행 잠금과 트랜잭션 범위 advisory lock만 추가했다. 영구 객체는 생기지 않는다.
- **API**: 경로·요청·응답 스키마·상태 코드 체계가 같다. 동작 변화는 두 가지다.
  - ① 동시 상황에서 늦은 요청이 잠깐 대기
  - ② 엑셀 동일 확정 이중 제출이 409 대신 200(순차 재전송과 같은 응답)
- **보안**:
  - SEC-01: 신규는 항상 INSERT, 키 위반은 409 → 회귀 테스트 통과
  - SEC-02: 감사가 업무와 같은 commit → 롤백 테스트 통과
  - RBAC·CSRF·세션: 전체 회귀 통과
  - 새 응답 필드·로그가 없어 개인정보 노출 경로도 늘지 않았다.

## 12. 남은 위험 및 미검증 항목
- **INT-I1(유지)**: 실제 문자 발송 도입 전 아웃박스 구조 필요(외부 I/O가 잠금·트랜잭션 안에 있음).
- **앱 밖 쓰기**: Java 레거시·직접 SQL은 부모 잠금 규칙을 따르지 않는다.
  - 기존 출결·점수 행 **값 변경**은 발송 잠금으로 막히지 않는다(FK와 무관한 UPDATE).
  - 새 행 삽입은 FK 잠금으로 막힌다.
  - 발송 전에 커밋된 변경은 기존처럼 감지된다.
- **휴원 경로**: 수강 SHARE ↔ 휴원 UPDATE 충돌은 코드 분석으로만 확인했다(테스트 없음). 출결이 있는 학생은 수강 대상 여부가 본문에 영향을 주지 않는다(`render`).
- **삭제**: 원본 행을 지우는 API는 없다(DB `RESTRICT`).
- **확정(approve)**: 잠그지 않는다. 그래서 확정 직후 원본이 바뀐 메시지는 '확정됨'으로 남을 수 있다. 발송 단계에서 차단되므로 성공 기록은 생기지 않는다. 이 메시지는 발송 시 409 후 취소·재생성해야 한다(기존 정책).
- **성능**: 잠금 보유 시간은 로컬 측정치다. 운영 규모 부하·원격 DB 지연은 측정하지 않았다.
- **보류된 검증**: 빈 DB 001→011 재구성, 개발 DB 불변조건 점검, 다중 인스턴스 실행(DB 잠금은 프로세스와 무관하게 동작).
- **11-3-A Informational(INT-I2~I6)**: 범위 밖이라 그대로 두었다.

- 필수 결함 4건을 모두 수정했다.

**질문: "이번 수정 이후 Academy LearningOps는 여러 직원이 동시에 출결·성적·메시지·수강 데이터를 처리하더라도, 기존 업무 불변조건을 일관되게 유지하는가?"**

**검증된 범위에서는 그렇다.** 검증 범위는 이 앱의 API 쓰기 경로, PostgreSQL 17.6, READ COMMITTED, 단일 프로세스 다중 요청이다. 그 범위에서 다음이 모두 테스트로 확인됐다.
- 출결·성적 동시 수정은 버전·행 잠금으로 하나만 반영된다.
- 메시지는 원본과 다른 내용으로 성공 기록되지 않는다.
- 같은 메시지는 한 번만 성공한다.
- 취소 수업에는 평가가 연결되지 않는다.
- 같은 엑셀 확정을 이중으로 보내도 중복 없이 같은 결과를 낸다.
- 다른 반 학생은 재사용되지 않는다.
- 업무 변경과 감사는 함께 저장되거나 함께 취소된다.

다만 **앱을 거치지 않는 쓰기(레거시·직접 SQL)와 실제 외부 발송은 이 보장의 범위 밖**이다.
