# 검토·발송: 반 단위 "목록 검토 → 선택 확정 → 일괄 모의 발송"

작업일: 2026-11-20 · 사용자 결정: 처리 구조 C(데이터 저장은 선택한 시간대 일괄 한 트랜잭션, 메시지 초안은 반별 생성, 발송은 사람의 검토 뒤) + 반 단위 일괄 검토·확정·발송

## 왜
기존에는 메시지 한 건마다 열고 → 검토 요청 → 확정, 다시 열고 → 모의 발송 → 확인을 했다(약 6번 클릭, 하루 77건이면 약 460번). 발송 쪽 클릭은 이미 확정한 내용을 다시 누르는 것뿐이다. 그렇다고 아무것도 보지 않고 일괄 확정하면 검토가 형식이 된다. 그래서 **읽는 단계는 남기고 기계적인 클릭만 줄였다.**

## 동작
'검토·발송' 탭이 **반 일괄 처리** 화면으로 열린다(전환: '한 건씩').
1. 수업 선택(기본: 오늘까지의 가장 최근 수업) → 그 수업의 취소되지 않은 메시지 **본문 전체**를 한 화면에 표시한다.
   - '확인' 열: `결석`·`인정결석`·`미응시`·`0점`(다시 볼 만한 사실, 막지는 않음), `원본 변경`(확정·발송 불가).
   - 요약: 검토 대기 · 확정(발송 대기) · 발송 실패 · 발송 완료 · 원본 변경 건수.
2. **선택 확정**: 기본 선택 없음. 본문을 읽고 체크한 메시지만 확정한다. 원본이 바뀐 메시지는 체크할 수 없다. 확인창에 수업과 건수를 표시한다.
   - **결석·인정결석 학생(2026-11-23 추가)**: 결석생 보호자는 데스크가 전화로 먼저 연락하는 경우가 많아, 결석생에게 보내는 메시지는 한 건씩 고르는 선택으로 둔다.
     - 표 머리글의 **전체 선택**은 `결석`·`인정결석` 메시지를 빼고 선택한다. 직접 체크해 둔 결석생은 유지된다.
     - 전체 선택을 다시 누르면 선택이 모두 해제된다.
     - 확정 버튼 옆에 "전체 선택은 결석·인정결석 N명을 빼고 선택합니다" 안내를 표시한다.
     - 확인창에 "이 중 결석 a건 · 인정결석 b건이 포함되어 있습니다. 보호자에게 이미 연락했는지 확인하세요."를 표시한다.
     - 판단 기준은 서버의 `attention` 표시이고, 초안 생성·확정·발송 규칙과 API는 바뀌지 않았다(프론트 `BatchReview.tsx`만 변경).
3. **일괄 모의 발송**: 확정된 메시지를 보내고, 발송 실패 메시지는 재시도한다. 확인창에 건수를 표시한다.
4. 결과는 학생별로 '확정 / 모의 발송 성공 / 모의 발송 실패(사유) / 제외(사유)'로 보여 준다.
5. 고칠 메시지는 체크하지 않고 학생 이름을 눌러 **한 건씩** 화면에서 수정·확정 취소·메시지 취소한다. 메시지 처리 현황에서 연 메시지는 처음부터 한 건씩 화면으로 열린다.

## 안전 조건 (구현 방식)
- 서버는 **기존 단건 함수**(`approve`, `mock_send`, `retry_mock_send`)를 메시지마다 차례로 호출한다. 그래서 메시지마다 다음이 그대로 적용된다.
  - 행 잠금과 `version` 비교(낡은 화면에서 누르면 `VERSION_CONFLICT`로 제외)
  - 원본 변경 검사(C-1, `SOURCE_CHANGED`로 제외)
  - 메시지별 멱등 키(응답을 못 받고 같은 요청을 다시 보내면 재생, 중복 발송 없음)
  - 메시지별 트랜잭션과 감사 기록(`details.batch = true`)
- 한 건이 제외되거나 실패해도 나머지는 계속 처리하고, 이미 처리한 건을 되돌리지 않는다. 반 전체를 '전부 아니면 전무'로 묶지 않는 이유는 발송이 외부 행동이기 때문이다(실제 발송기 도입 시 리뷰 M7 참고).
- 요청 범위는 수업 하나이고, 다른 수업의 메시지 id는 `NOT_IN_LESSON`으로 제외한다. 한 요청 최대 100건(초안 생성과 같은 한도). id 중복은 400. 권한·담당 반·CSRF 규칙은 단건과 같다.

## API (추가만)
| 경로 | 내용 |
|---|---|
| `GET /api/lessons/{id}/notifications/batch` | 수업의 활성 메시지: 목록 항목 + `body`, `source_changed`, `attention` |
| `POST /api/lessons/{id}/notifications/batch-approve` | `{items: [{id, version}]}` → `{results: [{id, student_name, outcome, code, message, replayed}]}` |
| `POST /api/lessons/{id}/notifications/batch-mock-send` | `{items: [{id, idempotency_key}]}` → 같은 형식. `APPROVED`는 발송, `MOCK_FAILED`는 재시도 |
단건 API와 동작은 바뀌지 않았다. 감사 상세에 선택 키 `batch`만 추가된다.

## 남은 위험·후속
- 발송기 호출이 메시지별 트랜잭션 안에 있는 구조(M7)는 단건과 같다. 실제 발송기를 붙일 때 함께 검토한다.
- 일괄 발송은 메시지를 순서대로 처리한다. 반 하나(4~5건)·모의 발송 기준으로는 짧지만, 실제 발송기에서는 응답 시간에 따라 요청이 길어질 수 있다(클라이언트 제한 120초).
- '검토 요청' 단계는 일괄 확정에서 건너뛴다(초안 → 확정). 단건 확정도 원래 초안에서 바로 확정할 수 있었고, 조교도 확정하는 운영(2026-11-18)과 맞다.
